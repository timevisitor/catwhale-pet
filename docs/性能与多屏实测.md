> 本文件是结论摘要。所有数字的原始出处在本机
> `H:\Hermes交付\猫鲸桌宠-UI与性能优化\electron\app\diag\electron-round2\`

## 1. 启动阶段的停顿（`--startuptest`）

- 主进程定时器打点（诊断副本）定位到两个固定延时任务，都压在启动最忙的几秒里：
  - `prewarmNode`（原 4000ms）：`execFile('node','-v')` 的同步段 **22～37ms**；
  - 更新检查（原 5000ms）：`fetch`/JSON 解析回来后的续体 **10～17ms**。
- 现在两者统一排进「窗口已显示 + 页面 `__petInitOK` 就绪」之后再等 **15s** 的空闲窗口
  （`scheduleStartupIdleTasks()`，页面迟迟不就绪最多等 8s 兜底）。日志：
  `STARTUP_IDLE_ARMED` → `STARTUP_IDLE_RUN`（实测 15.75～15.78s）→ `UPDATE_CHECK`（ok:true）。
- 交接报告里「4.5 秒处约 100ms」在本轮 4 次基线采样里只测到 **15～29ms**，没有复现；
  所以这次改动的依据是上面那份**逐回调归因**，不是「省了 100ms」。
- 启动早期还剩一个更大的单次回调：`did-finish-load` 后 250ms 的 `showPetWindow`
  （**34～61ms**，建窗显示 + 工作区校准 + 首轮页面脚本），属于窗口出现的那一刻，没有动。

## 2. 托盘隐藏 / 恢复（走游戏模式的隐藏路径）

托盘菜单没法用脚本点击，而生产代码里「隐藏」只有游戏模式这一条（`applyGameMode` → `win.hide()`），
所以用它的自动检测分支驱动（`settings.json` 的 `gameMode.extraProcs` 放一个测试进程名，
配合代码里已有的 `PET_GAMEMODE_POLL_MS` 把扫描周期调到 1.5s）：

| | 主窗口 | 灵动岛 | 进程数 | RSS | 单核 CPU | 视频 |
|---|---|---|---|---|---|---|
| 隐藏前 | 可见 | 可见 | 7 | 938 MB | 64% | idle 在播 |
| 隐藏后（1.3s 生效） | 否 | 否 | 5 | 866 MB | 37% | 暂停 |
| 恢复后（1.0s 生效） | 可见 | 可见 | 11 | 1101 MB | 73% | 继续推进（5 点采样 1614→2870ms） |

恢复后角色位移 4/4 步岛窗口都跟着动。**注意**：恢复后进程数/内存比隐藏前高
（7→11、938→1101MB），单次观测不足以判定泄漏，需要多轮循环才敢下结论。

## 3. 混合 DPI / 跨屏

- 本机 4 块屏：3×3840×2160@150%（DISPLAY1/2/3）+ 1×1920×1080@100%（DISPLAY5）。
- 逐屏（`petHost.setDisplay` 走托盘「所在屏幕」同一条 `moveToDisplay`）实测 **48/48 项通过**：
  主窗口物理矩形＝该屏工作区、`innerWidth/Height`＝工作区 DIP、`devicePixelRatio`＝该屏缩放、
  角色 CSS 尺寸恒定（372×620 DIP，物理 558×930 / 372×620）、灵动岛球心贴头顶（水平差 ≤28.5px、缝 8～15px）、
  岛与角色都在工作区内。
- 跨屏重启：切到 1920×1080@100%，拖到 (120,233)，退出重启 → `displayId` 与页面坐标都按原样恢复，
  且落在工作区内。
- 坑：跨屏比对**不能**用 `DIP × scale` 当期望值 —— 混合 DPI 下 Chromium 的 DIP 原点与尺寸不是同一个换算基准
  （1920×1080@100% 那块屏，Electron 报的 workArea 是 (395,1440) 而物理是 (593,2160)）。
  期望值要用 `GetMonitorInfo` 的物理工作区；同理 python 侧必须 `PER_MONITOR_AWARE_V2`，
  否则 `GetWindowRect` 会按主屏缩放折算（本机 ×1.5），跨屏全错。

## 4. 角色身上的 `drop-shadow`

20 秒窗口交替 3 轮（`#pet` 的 `filter` 开/关，同一进程内切换）：

- 单核 CPU 中位数：开 **30.22%**，关 **30.70%**（差值 −0.48 个百分点，噪声内）；
- 帧间隔中位数 8.3ms / p95 8.4～8.5ms、fps 119.5～120.0，两条件无差别。

**结论：不改**。合成器把滤镜放在 GPU 上，CPU 侧没有可见代价，不值得为它加配置项。

## 5. 交互延迟（供与 Tauri 对比）

CDP + `performance.now`，每项 5 次取中位数：

| 项 | 中位数 | 口径 |
|---|---|---|
| 右键 → SAO 菜单可交互 | **8.5 ms** | 面板有尺寸 + class=show + 焦点已落在菜单项 |
| 综合（情报）面板打开 | **4.5 ms** | `#hud` 有尺寸且 `HUDCTL.state().open` |
| 设置面板打开 | **4.6 ms** | `#settings` 有尺寸 + class=show |
| 聊天面板打开 | **1.4 ms** | `#chat` 有尺寸 + 焦点在输入框 |
| 灵动岛出现（窗口可见） | **1.56 ms** | Win32 `IsWindowVisible` 观察真实窗口 |
| 灵动岛内容出现 | **501 ms** | 受主进程 500ms 内容推送周期约束 |
| 灵动岛跟随 | **1.56 ms**（n=51） | 角色位移 → 岛窗口 x 变化（Win32 轮询真实窗口） |

- 页面内打点的分辨率 = 一个显示帧（本机 120Hz ≈ 8.3ms），所以个位数毫秒的项只能算「不超过一帧」。
- 灵动岛「出现」快但「内容」要等 500ms 推送周期：这是**架构性**的（`island.js` 的 `TICK_MS`），
  要更快就得让消息事件直推而非等轮询。

## 6. 测试

- 单元测试 27/27 个文件通过（含新增 `tests/startup-idle.test.cjs`：就绪前不跑 / ≥15s / 只跑一次 / 兜底 / 取消）。
- e2e（隔离配置目录）：panelmirrortest 10/10、walktest 22/22、mirrortest 19/19，页面异常 0 条。
- 设置面板的「检查更新」按钮手动点一次仍正常：提示「当前已是最新版本（v0.7.1）」，
  日志 `UPDATE_CHECK {"silent":false,...,"ok":true}`。

## 7. 已知取舍与遗留

1. 聊天预热挪到 15s 后：开机后 **15 秒内**发第一条消息，`resolveNode()` 会走同步兜底
   （`spawnSync('node','-v')`，本机平时约 100ms 级，卡住 8s 上限）。要彻底避免就得改成
   「打开聊天面板时再预热」。
2. 启动后第一次让角色动时，灵动岛可能先在屏幕右边缘露一下再吸附到头顶（`place()` 的门槛与
   夹取），观感问题，未处理。
3. 灵动岛内容延迟 500ms 是轮询周期决定的，未改。
4. 隐藏/恢复只跑了 1 轮循环，内存与进程数的上升不足以判定泄漏。
